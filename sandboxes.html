The disposable room where an agent's code can run

An AI agent writes code it has never been tested on, then wants to run it. A sandbox is the isolated, throwaway environment where that can happen without touching anything you care about. Here's what a sandbox is, what it's actually used for, and how one is wired into an agent.

🔒 not published — personal research, local only

TL;DR

A sandbox is an isolated, disposable environment for running untrusted code — here, the code an AI model generates on the fly. It exists because model output is unpredictable: models hallucinate packages, and a prompt injection can turn an agent into an attacker's tool.

The core use cases: code interpreters / data analysis, coding agents that build and test software, agent tool & computer use, running untrusted code at scale (incl. RL training), and ephemeral dev environments.

Under the hood it's a spectrum of isolation strength: plain container → gVisor → Firecracker microVM → full VM, trading stronger isolation against more startup cost. Firecracker boots a microVM in as little as 125 ms with under 5 MiB overhead.

01 · The problem

Why not just run the code?

A large language model (LLM) — the kind of AI behind tools like ChatGPT or Claude — can now do more than write text back to you. Give it the ability to execute code and it becomes an agent: it writes a script, runs it, reads the result, and decides what to do next, looping until a task is done.

That ability is exactly where the danger lives. The model is writing code no human reviewed, from a prompt that may itself be hostile, and then running it. If it runs on your actual machine, it runs with your permissions — your files, your saved passwords, your cloud credentials, your network.

Two failure modes drive the whole field:

Failure mode 1 — honest mistakes

Models are unpredictable and "routinely hallucinate entire packages." A generated script can delete the wrong directory, exhaust memory, or install a package that doesn't exist (or worse, one an attacker registered under the hallucinated name). No malice required — just a confident wrong guess.

Failure mode 2 — hijacking (prompt injection)

A prompt injection hides instructions inside data the agent reads — a web page, a file, an email — so the model follows the attacker instead of you. There is no reliable, deterministic way to prevent it. A sandbox can't stop the injection, but it contains the blast radius: a hijacked agent trapped in a sandbox can't reach your real secrets or systems.

So the goal isn't to make the code correct — it's to make running wrong or hostile code safe by construction. That is the job of a sandbox.

02 · Definition

What a sandbox actually is

A sandbox is "a dynamic environment that can ephemerally containerize code at runtime" — plainer: a walled-off, temporary computer-within-your-computer that the agent's code runs inside, and which you can throw away when it's done.

Three properties make it a sandbox rather than "just running the code somewhere":

1. Isolation. Code inside cannot see or touch what's outside — not the host's files, not its other processes, and (by default) not the network — unless you explicitly hand it a door.

2. Ephemerality. It's spun up for a task and destroyed after. Nothing the code did persists unless you deliberately save it, so a compromised or corrupted environment is discarded, not cleaned.

3. Constrained resources. It gets a fixed budget — CPU, memory, disk, wall-clock time — so a runaway or malicious job hits a wall instead of taking down the host.

The interesting engineering question is how strong the wall is, and what it costs you in speed. That's a spectrum, not a single answer.

03 · The isolation spectrum

How strong a wall do you want?

Every sandbox technology sits somewhere on a trade-off: the stronger the isolation, the more it costs to start and run. The key dividing line is whether the code shares the host's kernel — the core of the operating system. If it does, a single kernel bug can be an escape route. If it gets its own kernel, the host is far better protected.

A useful mental model: a container is a locked room in a shared house — walls, but everyone breathes the same air (the kernel). A microVM is a separate cabin with its own everything. gVisor is a clever middle option: it puts a software "kernel" in front of the real one so the code never talks to the host kernel directly.

04 · The use cases

What are they actually used for?

"Run untrusted code safely" shows up in several concrete shapes. These are the ones that matter for AI agents today.

01 · analysis

Code interpreter & data analysis

The agent writes and runs code to answer a question — parse a spreadsheet, plot a chart, crunch numbers — and reads the result back. The "run Python for me" feature behind many chat assistants.

e.g. ChatGPT / Claude analysis tools, Jupyter-style agents
02 · building

Coding agents

An agent edits a real codebase, then compiles, runs the test suite, and iterates on failures — all inside a sandbox so a bad build or a rogue script can't touch the developer's machine.

e.g. background coding agents, automated PR fixers, CI-style checks
03 · acting

Agent tool & computer use

The agent operates a whole environment — a shell, a browser, a virtual desktop — to do a task end to end. The sandbox is the computer it drives, kept separate from yours.

e.g. "computer use" agents, browser automation, virtual-desktop agents
04 · scale

Untrusted code at scale (incl. RL)

Run huge volumes of model-generated code and score it — to validate outputs, or to generate reward signals that train the next model. Needs thousands of disposable, parallel sandboxes.

e.g. reinforcement-learning environments, eval harnesses, AI-app hosting
05 · environments

Ephemeral developer environments

A fresh, ready-to-code machine conjured per task or per branch and torn down after — the same isolation tech, aimed at giving each agent (or human) a clean, throwaway workspace instead of a shared, drifting one.

e.g. per-task dev sandboxes, preview environments, remote code interpreters

05 · How it's wired in

The sandbox in the agent loop

A sandbox isn't a one-shot filter — it's a station the agent visits repeatedly. The model proposes code, the sandbox runs it, the results (including errors) come back, and the model adjusts. The wall sits between that loop and everything real.

Fig 2 — The agent proposes code; the sandbox runs it with its own kernel and resource caps and returns stdout/stderr/files; the model loops on the feedback. A hijacked or buggy run is trapped: the path to real secrets, host files, and the network is closed by default.

Two practical notes. First, the sandbox usually persists across the loop — the same session stays warm so the agent can build state (install a library once, keep files between steps) instead of paying startup cost every turn. Second, the door to the outside is opened deliberately: you grant a specific network allow-list or mount a specific folder, rather than starting open and locking down.

06 · Under the hood

How the wall is built

Four families, weakest to strongest. The honest summary: containers are fast but share the host kernel; microVMs give each job its own kernel behind a hardware boundary; gVisor is a software middle path; a full VM is the heavy, maximal option.

Numbers caveat: only Firecracker's figures are quoted from the official project — "initiates user space or application code in as little as 125 ms," "up to 150 microVMs per second per host," and "reduced memory overhead of less than 5 MiB." In practice, providers of agent sandboxes often build on Firecracker or gVisor precisely because "all LLM-generated code is treated as potentially malicious" — a zero-trust stance that pushes toward an own-kernel boundary rather than a shared one. Which you pick is a trade between how hostile you assume the code is and how much startup latency and operational complexity you'll accept.

07 · What to watch for

A sandbox is a boundary, not a force field

Isolation is necessary but not sufficient. The leaks are usually in the doors you opened, not the walls themselves.

1
Network egressThe most common leak. If the sandbox can reach the internet, a hijacked agent can exfiltrate data or pull in a payload. Default to no network; grant a narrow allow-list only when a task needs it.
2
What you mount inEvery file or credential you hand the sandbox is inside the wall. Mount the one repo it needs, not your home directory; pass scoped, short-lived tokens, never your primary keys.
3
Resource exhaustionWithout CPU/memory/disk/time caps, a runaway or deliberately abusive job can starve the host. Caps turn "take down the machine" into "this one job fails."
4
Escape bugsShared-kernel containers are one kernel vulnerability away from a host breach — the reason high-risk workloads move to gVisor or microVMs. Stronger isolation shrinks, but never fully removes, this surface.
5
Persistence & reuseReusing a warm sandbox across untrusted tasks lets one task poison the next. Ephemerality is a security property: when in doubt, throw it away and start clean.
The one-line takeaway

A sandbox contains the impact of untrusted code; it does not make the code trustworthy. Treat the model's output as hostile, keep the doors closed by default, and make the environment cheap to destroy.

08 · Glossary

Terms, defined once

LLM / agent
A large language model is an AI trained to predict text. It becomes an agent when given tools — like running code — and a loop to act, observe, and act again.
Kernel
The core of an operating system that controls hardware, memory, and processes. Whether untrusted code shares the host's kernel is the central sandbox-security question.
Container
A lightweight isolated process using Linux namespaces + cgroups. Fast and standard, but shares the host kernel — so isolation is only as strong as that kernel.
Namespaces / cgroups / seccomp
The kernel features containers lean on: namespaces give a private view of the system, cgroups cap resources, seccomp restricts which system calls are allowed.
Syscall (system call)
The way a program asks the kernel to do privileged things (open a file, use the network). Controlling syscalls is how sandboxes control what code can do.
gVisor
Google's open-source sandbox: a user-space "application kernel" (written in Go) that intercepts an app's syscalls and services them itself instead of passing them to the host kernel. Ships the runsc OCI runtime.
Sentry / Gofer
gVisor's two parts: the Sentry is the user-space kernel that handles syscalls; the Gofer is a separate process that mediates filesystem access over the 9P protocol, adding a layer of isolation.
MicroVM
A stripped-down virtual machine with only the devices a workload needs, giving hardware-enforced isolation at near-container speed. Firecracker is the best-known implementation.
Firecracker
AWS's open-source microVM technology built on KVM, purpose-built for secure multi-tenant code execution — boots in as little as 125 ms with under 5 MiB overhead.
KVM
Kernel-based Virtual Machine — the Linux feature that lets software create hardware-isolated virtual machines. The boundary microVMs rely on.
Prompt injection
An attack where hostile instructions are hidden in data the model reads, hijacking its behaviour. Sandboxes can't prevent it but can contain what a hijacked agent is able to reach.
Ephemeral
Created for a single task and destroyed after. For sandboxes it's a safety feature: a corrupted environment is discarded, not repaired.
Egress
Outbound network access from inside the sandbox. Often the weakest link, since it's the path data can leave by.
