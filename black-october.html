Read this first

  1. Contain exposed credentials first. LiteLLM confirms a malicious release; Railway reports possible access to customer secrets. Check actual artifact execution and stored-secret exposure, then revoke credentials and rebuild where appropriate. [1] [2] [3]
  2. Patch exposed services promptly. PHP and VeloCloud have reported exploitation activity. GitLab and Node.js have major security updates; their advisories are not evidence that all affected installations were breached. [4] [5] [6] [7] [8]

What “Black October” means here

This is the title of this briefing, not an established name for one coordinated campaign. These are distinct events. The public evidence reviewed does not establish a shared attacker or a single root cause.

“Last 48 hours” is a reporting window. Only LiteLLM’s release compromise is precisely timed here. Other items are labeled as detection, disclosure, patching, or updates; unknown intrusion dates stay unknown. This is a selected public-source briefing, not an exhaustive incident census.

§ 2Ten developments, with evidence labels

Filter by the kind of evidence. “Incident” includes confirmed compromise, possible secret exposure, and reported disruption; each entry states which. “Patch / disclosure” does not imply observed exploitation.

01 · Supply-chain compromise

LiteLLM: the release itself was malicious

Occurred in window · Oct 21 · Confirmed by maintainer

LiteLLM, a gateway and Python library for calling AI models, shipped malicious 1.107.0 artifacts through PyPI, Docker Hub, and GHCR. The payload stole credentials and installed a remote-code loader. The official GitHub source tag was clean: the compromised release workflow built from an attacker-controlled lookalike repository. [1]

Exposure window: the maintainer gives PyPI as 11:39:51–13:23 UTC on October 21, Docker Hub as 11:46:56–14:20 UTC, and GHCR as beginning 11:46:56 UTC and unavailable by 13:51 UTC. Affected container tags included v1.107.0, latest, main-latest, and main-stable. Cached copies can still execute after registry removal. [1]

Observed consequence: Wiz reports use of stolen AWS role credentials between 16:20 and 17:01 UTC, including identity and model-enumeration calls. This is evidence of downstream credential abuse, not merely a malicious package upload. [2]

Act: isolate affected environments, preserve evidence, revoke and rotate every reachable secret from a clean system, and rebuild from verified artifacts. The maintainer recommends pinning 1.106.2 for this incident. Avoid starting Python or pip in a suspect environment: Python startup can execute the malicious files again. Private enterprise-registry releases were unaffected according to LiteLLM. [1]

Still open: LiteLLM suspects exposed gateway logs containing GitHub CLI OAuth tokens enabled the intrusion. The initial access mechanism remains unconfirmed. The report does not establish a common attacker with Railway. Registry takedown estimates differ between sources; this briefing uses the maintainer’s artifact-specific timeline. [1] [2] [3]

02 · Possible customer-secret exposure

Railway: stored environment variables may have been accessed

Detected and disclosed in window · Oct 21 · Scope under investigation

Railway detected anomalous activity on systems storing customer environment variables. Its investigation indicates that an unauthorized party may have accessed encrypted variables and decrypted some of them. These variables can contain API keys, database passwords, and private-registry credentials. The provider describes a possible subset of users; it has not supplied a verified affected-user count in this disclosure. [3]

Act: Railway recommends all customers immediately rotate stored environment variables containing secrets and private-registry credentials, then review the corresponding services for unusual activity. Revoke credentials at their issuing services; merely changing a stored value does not revoke a stolen key. Coordinate redeployment with current service availability. [3]

Timing and uncertainty: October 21 is the detection and disclosure date, not an established first-access date. Railway believes the activity targets AI inference providers; that is its assessment, not independently established attribution. The original disclosure paused deployments, so it should not be used as a live service-status page. [3]

03 · Runtime vulnerabilities

PHP2Shell: emergency patches, with exploitation activity

Patch and new exploitation reporting in window · Oct 21

CVE-2026-109618 and CVE-2026-109619 affect the PHP runtime used to serve web requests. PHP’s advisory includes PHP-FPM, Apache mod_php, php-cgi, FrankenPHP, and LiteSpeed; it considers mod_php the highest-risk deployment, with demonstrated unauthenticated execution before application code runs. Updating an application alone does not update the runtime beneath it. [4]

Install: PHP 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35, or a distribution package with the relevant fixes backported. Restart the serving processes and rebuild affected container images. PHP and AWS say configuration-only workarounds do not fully remediate both flaws. [4] [5]

Exploitation evidence: AWS reports an October 17 attempt and further attempts on October 21 before the 14:00 UTC release, followed by broad exploitation activity. Its technical analysis does not establish that the sampled pre-release attempts would have succeeded against real-world systems. Do not translate honeypot attempts into a count of breached organizations. [5]

Investigation window: review relevant logs from at least October 17, extending before this briefing’s reporting window. October 21 is the patch/reporting event; it is not the beginning of exploitation. [5]

04 · Network management

VeloCloud: a low-privilege account can become an operator

New advisory in window · Oct 22 · Vendor confirms active exploitation

Arista’s CVE-2026-114625 is an SQL-injection vulnerability in VeloCloud Orchestrator. An attacker needs network access and a valid authenticated session; even the Enterprise Read Only role is sufficient to gain operator privileges and impersonate a local superuser operator. This is not an unauthenticated flaw. Arista rates it 9.9 under CVSS 3.1 and 9.4 under CVSS 4.0. [8]

Install: 5.2.3.18 / 6.1.3.10 / 6.4.2.12 on the corresponding VCO release train. Hosted and Dedicated orchestrators have already been patched, according to Arista. VeloCloud Edge and Gateway are not affected by this specific vulnerability; end-of-support versions were not assessed. [8]

Act: restrict the management interface to trusted administrative networks while upgrading; investigate unexpected administrator changes, outbound connections, and webshells. Preserve relevant logs before remediation where feasible. Arista confirms exploitation but does not date its onset or identify victims in the advisory. A patch does not by itself demonstrate removal of an existing intruder. [8]

05 · Development infrastructure

GitLab: critical unauthenticated server-code execution

Patch released in window · Oct 21 · Exploitation not established here

CVE-2026-110264 is an integer overflow during regular-expression compilation that can permit unauthenticated code execution under certain conditions. GitLab rates it CVSS 3.1: 10.0. Affected CE/EE versions extend back to 7.0, so old self-managed deployments need attention too. The score describes potential severity; it is not proof of an actual breach. [6]

Install on the appropriate upgrade path: 19.5.1, 19.4.3, 19.3.6, 19.2.9, 19.1.9, 19.0.10, or 18.11.13. GitLab.com is already patched. GitLab Dedicated tenants on 19.3.5-internal0 or 19.4.2-internal0 or later already have the fix. [6]

Act: inventory self-managed instances, follow GitLab’s supported upgrade procedure, and review its published “Onigmo native worker crash” and “Org mode render error burst” detections. The examined advisory establishes the vulnerability and fix, not confirmed victim compromise. [6]

06 · Application runtime

Node.js: Brotli memory corruption and nine other fixes

Security releases in window · Oct 21 · Exploitation not established here

Node.js patched ten vulnerabilities across its supported 22.x, 24.x, and 26.x lines. The project describes CVE-2026-111497 as a Brotli decoder out-of-bounds write permitting remote code execution, rated High. Other fixes address DNS truncation, TLS hostname checks, randomness caches, and permission checks. Not every issue affects every line. [7]

Install: 22.23.4 / 24.22.1 / 26.12.1. Update deployed runtimes and images, including workers and build environments; changing an npm dependency lockfile alone does not replace Node.js. End-of-life lines should move to a supported release. The releases also include updates concerning the eMudhra CA incident. [7]

Evidence boundary: the advisory establishes affected versions and potential impact. It does not establish exploitation or a production breach. Treat it as urgent patch work without labeling every Node.js service compromised. [7]

07 · Linux file sharing

KSMBD: public reports ahead of a confirmed fix

New disclosure coverage in window · Oct 22 · Technical details partly secondary

The Hacker News reports two KSMBD remote-code-execution issues, ZDI-CAN-33774 and ZDI-CAN-33549, with reported CVSS scores of 9.0. The first concerns protocol dispatch before authentication; the second requires SMB Direct/RDMA and a writable share. These are KSMBD-specific reports, not a claim that every Linux installation is remotely exploitable. [9]

Evidence quality: ZDI’s rolling list independently corroborates ZDI-CAN-33774, its Linux target, score, and October 21 reporting date. The original mailing-list pages were inaccessible behind a bot challenge, so the technical detail and absence of a mainline fix rely on the secondary report. No in-the-wild exploitation is established by the examined evidence. [9] [10]

Act: identify hosts actually serving KSMBD, restrict SMB access to required networks, and disable unused KSMBD service after assessing operational impact. Confirm current patch availability with the distribution/vendor before choosing a kernel version; this briefing does not invent a fixed release. [9]

08 · Public-service disruption

Columbia, South Carolina: city systems disrupted

Reported in window · Oct 22 · Intrusion onset and data loss unspecified

The Record reports, quoting a city spokesperson, that Columbia is responding to a cyberattack and that South Carolina’s SLED is leading the investigation. Affected systems include MyColaSC, geographic-information systems, and animal services. The city said police, fire, 911, water systems, and the Payment Center—including online payment services—remained operational. [11]

What is established: a reported cyberattack with service disruption. The report does not confirm ransomware, stolen data, a perpetrator, or the precise start of the intrusion. October 22 is its publication date. It would be misleading to classify this as a confirmed data breach or an attack proven to have begun in these 48 hours. [11]

Operational lesson — analysis: maintain alternate service channels and distinguish unavailable portals from failures of underlying critical services. No action against Columbia’s systems is part of this research.

09 · New attribution for an earlier incident

ConnectWise: Microsoft details ARTEX-assisted activity

New analysis in window · Oct 21 · Campaign and initial disclosure predate it

Microsoft attributes the ConnectWise Cloud Backup supply-chain compromise to the China-state-aligned actor it calls Storm-0940. It describes use of the ARTEX agent framework to accelerate reconnaissance, password spraying, and OAuth-application abuse. Its telemetry places the broader campaign as early as September; ConnectWise’s initial advisory was October 16. This is a new intelligence update, not a new October 21 breach. [12]

Act if the integration was authorized: follow current vendor containment guidance, preserve Entra sign-in and audit evidence, and inspect service-principal credentials, consent grants, role assignments, and Microsoft Graph activity. Microsoft advises keeping affected connections disabled pending formal restoration instructions, and not deleting enterprise applications as the first response. [12]

Interpret carefully: targeting, failed logins, successful authentication, persistence, and data exfiltration are different observations. Microsoft explicitly cautions that an affected application or successful sign-in alone does not prove data access. AI assistance does not establish a link to the other incidents in this briefing. [12]

10 · Certificate-trust fallout

eMudhra: certificate replacement becomes an operational deadline

Business-exit announcement in window · Oct 22 · Weak-key discovery Oct 17

eMudhra announced its exit from the global SSL/TLS certificate business on October 22, following the earlier weak-key incident. Google says eight subordinate CA private keys had insufficient randomness; the initial report arrived on October 17. eMudhra says its infrastructure was not compromised and no data was breached. A cryptographic trust failure must not be silently relabeled a network intrusion. [13] [14]

Act: inventory certificates chaining to emSign ECC Root CA - G3 and replace them with a certificate from another trusted hierarchy. Google plans root removal for October 27, Pacific time; legitimate certificates under that root will also stop working. Update runtimes and trust stores through their supported mechanisms, including the Node.js release above. [14] [7]

Timing: the discovery and initial browser blocking are outside the reporting window. The October 22 exit announcement and resulting migration work are the included development. Google’s account limits claims about abuse: no certificates from the six TLS intermediates were logged to CT before its blocking action, protecting CT-enforcing clients. [13] [14]

Analyst recommendations: prioritize actual deployment and exposure over headline severity. This research did not inspect XO infrastructure and does not establish that XO uses, or was affected by, any listed product.

What ties the response work together

Analysis: several developments put credentials or delegated trust at risk: package execution can steal keys; a platform can expose stored secrets; an OAuth application can retain access after a vendor response; a certificate authority can undermine authentication. The practical question is not only “Did we patch?” but “What access could already have escaped, and have we revoked it?” This is a shared defensive concern, not a claim of common attribution. § 4Method, exclusions, and open questions

The cutoff was fixed when research began: October 22, 2026 at 20:41:08 UTC, minus exactly 48 hours. Discovery used The Hacker News and The Record feeds, followed by opening the cited vendor advisories, researcher reports, and CISA catalog. RSS timestamps were normalized to UTC; an article showing October 23 in UTC+05:30 can still fall on October 22 UTC. Sources were accessed October 22; no archived snapshot of every page at the cutoff was available. [17] [18] [19]

Selection favors consequential public disclosures, exploitation, patches, and material updates. Publication time is not intrusion time. The briefing uses “confirmed” for what a provider or cited observer actually reports, preserves “may” and “suspected,” and distinguishes vendor assessment from independent observation. CVSS version numbers are supplied when scores are compared.

Headlines deliberately kept outside the count

  • OpenCode MCP OAuth RCE: Pillar’s original report is dated October 19 and the fix, 1.18.33, was released September 28. October 22 coverage does not make it a new vulnerability inside this window. Relevant background for Windows/WSL users, but excluded from the ten developments. [16]
  • QPACK / HTTP/3 “Header Accordions”: FoxIO’s timeline says October 20 publication without a precise time. Some fixes date to 2025 or earlier in 2026. Because publication cannot be placed after the 20:41:08 UTC start boundary, it is excluded from the strict-window count. The original report remains useful for affected HTTP/3 deployments. [15]
  • Earlier CISA additions: the retrieved KEV snapshot has October 20 date-only additions. A catalog addition is not the date exploitation began, and the day alone cannot establish inclusion after this window’s evening start. Absence from KEV is not evidence of safety. [19]

What remains unresolved

  • LiteLLM’s initial access mechanism and full downstream impact; Railway’s first-access date, affected-account count, and extent of plaintext access. [1] [3]
  • The onset and victim scope of VeloCloud exploitation; actual customer compromises attributable to PHP attempts in the examined telemetry. [8] [5]
  • KSMBD patch availability by distribution; Columbia’s initial-access route, ransomware status, and any data theft. [9] [11]

Coverage limits: BleepingComputer and SecurityWeek returned HTTP 403 during discovery; two kernel mailing-list pages returned a bot challenge. KSMBD therefore has explicitly lower verification depth. Public notices can be incomplete or revised. No exploit was run, no third-party system was probed, and download totals or targeted tenants were not treated as confirmed victims.

A short glossary

Vulnerability / exploit / breach
A vulnerability is a weakness; an exploit uses it. A breach or compromise requires evidence of unauthorized access or impact. A vulnerability announcement alone is not a breach.
RCE
Remote code execution: an attacker can cause a remote system to run code. Preconditions differ between vulnerabilities.
Supply-chain compromise
An attacker abuses trusted software distribution or a third-party integration to reach downstream users.
Secret rotation
Replace a credential and invalidate the old one at its issuer, then update legitimate consumers. Removing the old value from a configuration file is not enough.
CVSS / CVE / ZDI-CAN
CVSS scores technical severity; a CVE identifies a vulnerability. ZDI-CAN is a researcher’s tracking identifier and should not be presented as a CVE.
