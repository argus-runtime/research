They deleted most of rewrote the prompt.

Anthropic — the AI company behind the Claude models — says it removed over 80% of the standing instructions inside Claude Code, its AI coding assistant, because its newest models no longer need them. This is a read of the blog post explaining why, and what the new rules of "context engineering" are.

Source claude.com/blog Author Thariq Shihipar, member of technical staff, Anthropic Published Jul 24, 2026 Read time ~5 min original

TL;DR

  1. Anthropic removed over 80% of Claude Code's system prompt for its newest models (Claude Opus 5 and Claude Fable 5) with, in its words, "no measurable loss on our coding evaluations."
  2. The reason: old prompts were full of strict rules written to protect against the worst-case behaviour of older models. Newer models "have better judgement and can handle these decisions well without explicit rules."
  3. Six former best practices are declared myths, each with a replacement: rules → judgement, examples → interface design, everything-upfront → progressive disclosure, repetition → simple tool descriptions, manual memory files → auto-memory, simple specs → rich references.
  4. Practical upshot for anyone configuring an AI agent: make every instruction file shorter, keep only codebase "gotchas," split long guidance into files loaded on demand, and prefer showing the model real code over describing what you want in prose.
  5. Caveat: this is a vendor writing about its own product, and the "80%" and "no measurable loss" figures come from internal evaluations. Trust the shape of the argument more than any single number.

§ 1What this is about, from zero

Claude is a family of large language models — AI systems that read and write text — made by Anthropic, one of the major AI labs. Claude Code is Anthropic's coding assistant built on those models: a program that sits in a developer's terminal or editor, reads their codebase, and writes and edits code on request. The newest generation of models, released in 2026, includes Claude Opus 5 and Claude Fable 5 — the "Claude 5 generation" of the title.

When you type a request to an AI assistant, your message is not all the model sees. Behind the scenes, the software wraps your message in a much larger bundle of standing text: instructions about how to behave, notes about your project, descriptions of the tools it may use, memories from earlier sessions. The article's own framing:

"When you send a message to Claude, the prompt is only a small part of the context it gets. Much of your context is assembled from your system prompt, Skills, CLAUDE.md files, memory, and other sources. We call this context engineering." — the article (claude.com blog, Jul 24, 2026)

Context engineering, then, is the craft of deciding what goes into that bundle. It is harder than writing a one-off prompt because, as the article notes, "context is used generally across many requests, so it cannot be as specific" — you are writing standing instructions without knowing what the user will ask.

Why is that impressive? A system prompt is the product team's main lever over how the assistant behaves — teams typically grow it over time, adding a rule for every incident. Deleting most of it and losing nothing on evaluations (if the internal figures hold up) means the rules weren't doing the work anymore; the model's own judgement was. Anthropic has folded these lessons into a diagnostic command, claude doctor (run as /doctor inside Claude Code), which the post says will "rightsize your skills, and CLAUDE.md files."

§ 3Why the rules stopped paying rent

The post's diagnosis is that Claude Code was being overconstrained — by its own system prompt and by users' configuration files alike. Reading transcripts of internal usage, the team found "several conflicting messages in a single request" as different instruction sources clashed:

"leave documentation as appropriate" CLASHES WITH "DO NOT add comments"

Both real examples from the article — one instruction arriving from a skill or user request, the other from the system prompt. The model usually untangles the contradiction, but "must think more carefully about these overlapping and conflicting messages before deciding what to do" — wasted effort on every request.

Two things changed. First, capability: the strict rules existed "to avoid worst case scenarios" (the post's example: deleting files) in older models, and the team "found we can delete many of them and let the model use surrounding context and judgement instead." Second, infrastructure: Claude Code once leaned on a single project-notes file, CLAUDE.md, as "a source of memory, information, and guidance." It now has dedicated features — "memory, artifacts, and skills, which Claude can use to create new ways of loading and sharing context across sessions" — so the one big file no longer has to carry everything.

§ 4Six myths, six replacements

The core of the article is a list of former best practices that "had become myths," each paired with what to do instead. Struck-through = the old advice.

SHIFT 1 / 6
Give Claude rules→Let Claude use judgement

Old prompts hard-coded behaviour to prevent worst cases, even where the rule was sometimes wrong. The clearest before/after in the piece is about code comments — the actual system-prompt text:

Then — old system prompt (verbatim)In code: default to writing no comments. Never write multi-paragraph docstrings or multi-line comment blocks — one short line max. Don't create planning, decision, or analysis documents unless the user asks for them — work from conversation context, not intermediate files.
Now — new system prompt (verbatim)Write code that reads like the surrounding code: match its comment density, naming, and idiom.

The old rule failed users who wanted documentation, or code genuinely needing long comments. With older models that trade-off was accepted because unguided comments "would be incorrect in many cases." Newer models "have better judgement and can handle these decisions well without explicit rules."

SHIFT 2 / 6
Give Claude examples→Design interfaces

"The number one rule for tool usage was to give Claude examples on how to use them." No longer: with the newest models, "giving examples actually constrains them to a certain exploration space" — the model imitates the sample instead of thinking. The replacement is to make the tool itself self-explanatory: "think more about the design of your tools, scripts and files — what parameters does Claude have and how can they be more expressive?" The post's example is a to-do-list tool where simply listing the allowed status values — pending, in_progress, completed — "hints to Claude about how to use it," and one line ("keep one item in_progress") defines the wanted behaviour with no worked examples at all.

SHIFT 3 / 6
Put it all upfront→Use progressive disclosure

Progressive disclosure = loading "the right context at the right times" instead of front-loading everything. Detailed code-review and verification instructions moved out of the always-on system prompt into skills — separate instruction files the assistant opens only when relevant. Tools get the same treatment: some are "deferred loading," meaning "the agent must search for their full definitions using ToolSearch before using them," so rarely-used tools cost nothing until needed.

SHIFT 4 / 6
Repeat yourself→Simple tool descriptions

"Earlier Claude models could sometimes need repeated instructions or be more likely to listen to instructions at the end of their context window than at the start" — so the same guidance was written twice, once in the system prompt and again in the tool's own description. For the new models, "we could delete these repeat examples and put instructions on how to use tools in the tool descriptions rather than the system prompt." One home per instruction.

SHIFT 5 / 6
Memory in CLAUDE.md files→Auto-memory

Users used to curate the assistant's memory by hand — "using the # hotkey to write to their CLAUDE.md automatically." Now: "Claude now automatically saves memories that are relevant to the work and to you." Memory becomes something the model maintains, not something the user files.

SHIFT 6 / 6
Simple specs→Rich references

Plans and specifications used to live in plain markdown files the assistant re-read as it worked. The claim: "Claude can handle increasingly more complicated references." Three richer forms are named: HTML artifacts (interactive documents the assistant itself produces) instead of markdown plans; code as spec — "a spec may also be a detailed test suite, or a function in a different codebase that Claude might port"; and rubrics, scoring guides that "allow Claude to try and verify your taste in a particular field (e.g. what does a good API design look like) by using dynamic workflows and spinning up verifier agents with those rubrics."

§ 5The advice, layer by layer

The post closes with per-layer guidance for assembling your own context — whether you're configuring Claude Code or building an agent from scratch.

System prompt

"Heavily tied to the product context" — it tells the model what product it's in and what it's doing. Claude Code users "will likely never modify this"; but "if you are building your own agent harness, this is where you should spend a lot of time."

CLAUDE.md

"Keep your CLAUDE.md lightweight and briefly describe what your repo is for, but spend most of the tokens on gotchas inside of the codebase" — e.g. a convention like keeping all types in one monolithic file. "Avoid stating 'the obvious' things Claude should know by looking at your file system or your repo," and push long procedures (like verification steps) out into a skill referenced from the file.

Skills

"Lightweight guides to let Claude find information when needed. Avoid making them overconstrained, except in highly important areas." Split long skills into many files (progressive disclosure again). Best used to "encode particular opinions, knowledge, or best practices that are particular to you, your team, or product."

References

Files you @-mention into the conversation — specs, mockups, "or even entire codebases." Prefer code-shaped references: "a HTML mockup of a design will generally produce better results than a description of the design or a screenshot," because code is "a language it knows very well."

If you configure any AI agent, the to-do list is:

  • Audit your standing instructions for rules that exist to prevent a failure mode the current model no longer has — delete them and state the goal instead.
  • Hunt for contradictions between your instruction sources (system prompt vs. project file vs. skills) — every clash costs the model effort on every request.
  • Replace worked examples in tool definitions with better-designed parameters (expressive names, enumerated values, one behavioural constraint).
  • Break monolithic instruction files into a small always-loaded core plus on-demand files.
  • Say each instruction once, in the place it belongs — tool guidance in the tool description, not the system prompt.
  • Hand the model real code (tests, mockups, a reference implementation) instead of prose describing what you want.
  • In Claude Code specifically: run /doctor to get this audit done automatically.

Read with care — vendor source

This is Anthropic writing about Anthropic's product and Anthropic's models, published on its own blog. The two load-bearing numbers — "over 80%" of the prompt removed, and "no measurable loss" — come from internal, unpublished evaluations; neither the old and new prompts' sizes nor the evaluation suite is disclosed, and "no measurable loss" is doing quiet work (it bounds what their tests detect, not what changed). The post also promotes new product features (auto-memory, artifacts, /doctor). The direction of the argument — newer models need fewer guardrails, and over-instruction now has a real cost — is consistent with the trend across the industry, and is the useful takeaway. Trust the shape, not the point estimates.

§ 6Glossary

large language model (LLM)
An AI system trained on huge amounts of text to read and generate language; Claude is one.
prompt
The message a user types to the model for one specific request.
context / context window
Everything the model reads when producing an answer — the prompt plus all standing instructions and files. The context window is the maximum amount of text (measured in tokens, roughly word-fragments) it can read at once.
context engineering
Designing the standing part of the context: which instructions, files, and tool descriptions get bundled with every request, and when.
system prompt
The product's built-in standing instructions — invisible to the user, sent with every request, defining how the assistant behaves.
Claude Code
Anthropic's AI coding assistant; runs in the terminal, editors, and the web, and can read and edit real codebases.
CLAUDE.md
A plain-text notes file in a user's project that Claude Code reads automatically — project conventions, warnings, preferences.
skill
A packaged instruction file for one kind of task (e.g. "how we do code review") that the assistant loads only when that task comes up.
tool / tool description
An action the assistant can take (run a command, edit a file), defined with a short text description telling the model when and how to use it.
deferred loading / ToolSearch
Keeping a tool's full definition out of the context until the assistant searches for it — so many tools can exist without all of them costing space on every request.
progressive disclosure
The design principle of revealing information only when it becomes relevant, rather than all upfront.
auto-memory
Claude Code's newer feature where the assistant saves relevant facts across sessions by itself, replacing hand-curated memory notes.
artifact
A self-contained document (often interactive HTML) the assistant produces and can later re-open as a reference.
spec
A specification — a written description of what software should do; the post argues a test suite or example code often beats a prose spec.
rubric
A scoring guide describing what "good" looks like in some domain, which the assistant can hand to checker ("verifier") agents to judge work against your taste.
agent / agent harness
An AI system that works toward a goal by taking actions (using tools) over multiple steps; the harness is the surrounding software that feeds it context and executes its actions.
evaluation (eval)
A standardised test suite for measuring a model or product's performance; "no measurable loss on our coding evaluations" means Anthropic's internal test scores didn't drop.
